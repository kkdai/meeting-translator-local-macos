# 實作路線圖

日期：2026-08-04
狀態：草案

依 [feasibility](2026-08-04-feasibility.md) 與 [architecture](2026-08-04-architecture.md) 文件展開的分階段計畫。每個階段結束都應該有一個可實際操作、可驗證的產出，而不是只有程式碼。

---

## Phase 0 — 技術驗證 Spike（先做，不寫產品程式碼）

**目的**：驗證 feasibility 文件裡最大的未知數 — WhisperKit 串流 + MLX Gemma 4 能否在 M4 / 16GB 上同時跑，延遲是否真的「快速」。

- [ ] 建一個最小 Swift command-line 或單頁測試 App：麥克風／檔案音訊 → WhisperKit 串流轉錄，量測 partial result 延遲
- [ ] 獨立測試 MLX Gemma 4 E4B 與 E2B 的單句翻譯延遲（英文/日文 → 繁中），記錄 tokens/sec 與首字延遲
- [ ] 兩者同時載入，量測記憶體峰值與是否互相搶資源導致降速
- [ ] 用 Whisper 直接轉錄中文語音，確認簡體/繁體傾向，驗證 OpenCC s2twp 轉換後的可讀性
- [ ] 產出：一份簡短的量測結果記錄（延遲、記憶體），回頭修正 feasibility 文件中「待驗證項目」的結論，必要時調整預設模型大小（E2B vs E4B、tiny/base/small）

**不通過的訊號**：若端到端延遲（音訊→字幕）明顯慢於原雲端方案，或 16GB 機型記憶體壓力大到影響會議軟體本身運作，需要重新評估模型選型（例如降級到 Whisper tiny + Gemma 4 E2B）再決定是否繼續。

## 里程碑判斷準則

每個 Phase 完成的定義是「可以實際操作看到功能運作」，不是程式碼寫完但沒驗證。沿用原專案的驗證方式（專案沒有 XCTest，靠手動跑情境）：至少要跑過一次「正常流程」「邊界情況（極短會議）」「錯誤情況（模型載入失敗／記憶體不足）」三種情境，且錯誤情況不能讓 App crash 或遺失已完成的逐字稿。
