# 可行性評估：本地 STT + Gemma 4 翻譯

日期：2026-08-04
狀態：草案（待實機驗證）

---

## 目標與限制

- **硬體基準**：MacBook（Apple M4，假設 16GB 統一記憶體為最低支援規格；24GB+ 視為進階體驗）。
- **STT 要求**：「快速」、即時顯示**繁體中文**字幕。原文語言不限（英文、日文…），也可能本來就是中文。
- **翻譯要求**：使用比較小的本地模型處理翻譯 — 對應 Google 於 2026-04-02 發布的 **Gemma 4** 系列中最小的變體（E2B / E4B），而非舊版 Gemma 3。
- **完全離線**：不可依賴任何雲端 API（這是與原專案最核心的差異）。
- **延續原專案 UX**：懸浮字幕、雙語逐字稿匯出、會議筆記、網頁匯出。

---

## STT 選項評估

| 方案 | 優點 | 缺點 | 結論 |
|---|---|---|---|
| **WhisperKit**（Argmax，2026-05 起併入 `argmax-oss-swift` v1.0，MIT） | Core ML + ANE + Metal 原生加速；官方數據 base model（142MB）在 Apple Silicon 上達 >15x real-time（5 秒音訊約 0.3 秒處理完）；原生支援串流即時轉錄；多語言（沿用 Whisper 的 ~99 語言，含中/英/日/韓等會議常見語言）；MIT 授權；macOS 13+ 即可用，不綁定最新系統 | 需要下載模型權重（首次啟動）；中文輸出偏簡體，需後處理轉繁體 | **首選**：多語言穩定度與相容性最符合「會議來源語言不固定」的需求 |
| **Apple `SpeechAnalyzer` / `SpeechTranscriber`**（macOS 26 Tahoe+ 原生框架） | 完全免模型下載；ANE 加速下英文場景實測比 Whisper Small 快 ~3 倍、WER 更低；系統內建、零額外體積 | 僅 macOS 26+ 可用（排除較舊系統使用者）；官方測試多集中在英文，多語言／中文的 on-device 覆蓋與品質尚待驗證；客製化空間（如強制輸出格式、串流細節）不如 WhisperKit 成熟 | **候選 / 快速跟進項**：可作為 macOS 26+ 使用者的可選加速後端，但不作為 v1 唯一依賴 |
| whisper.cpp（純 C++，手動 Core ML 編碼器） | 社群成熟、可控性高 | 需要自行處理 Swift 橋接、串流管線、記憶體管理，工程成本高於直接用 WhisperKit（本質上是同一套 Core ML Whisper，WhisperKit 已經做好這層） | 不採用，WhisperKit 已覆蓋其優點且封裝更完整 |

**建議**：v1 以 **WhisperKit** 為唯一 STT 後端（模型選 `small` 或蒸餾版本，在速度與多語言準確度間取平衡；可在 UI 提供 tiny/base/small 選擇）。`SpeechAnalyzer` 列為 Phase 2+ 的可選加速路徑，待驗證中文與多語言 on-device 品質後再決定是否納入。

## 翻譯（MT）選項評估

Gemma 4（2026-04-02 發布）規格：E2B（~2.3B 有效參數）、E4B（~4.5B 有效參數）、26B A4B（MoE）、31B（dense）。E2B/E4B 支援文字＋圖片＋**音訊**輸入、純文字輸出，128K context，Apache 2.0，140+ 語言。

| 執行方式 | 優點 | 缺點 | 結論 |
|---|---|---|---|
| **MLX（MLX Swift）** | Apple 官方框架，直接呼叫 Metal，效能最佳（社群評測顯示比 Ollama 快 10-20%）；已有社群的 Gemma 4 MLX Swift 原生實作可參考；可直接整合進 App 進程內，無需額外背景服務 | 需要自行管理模型下載、量化版本、記憶體釋放；MLX Swift 生態相對新，API 穩定度需留意 | **首選**：效能與整合度最佳，且是與 WhisperKit 一致的「App 內直接跑」架構 |
| **Ollama（本地 REST API，`localhost:11434`）** | 整合極簡單（HTTP call）；模型管理、量化、更新都由 Ollama 處理；開發速度快 | 使用者需另外安裝 Ollama App 並手動 pull 模型，增加安裝步驟；效能略遜於 MLX 原生；多一個外部進程依賴，不符合「單一 App 直接可用」的產品體驗 | **備案**：可作為開發階段的快速原型驗證管道，正式產品不建議依賴外部進程 |
| llama.cpp + GGUF | 成熟、可控 | 需自行維護 Swift 綁定，量化格式與 MLX 生態分離，無額外優勢 | 不採用 |

**建議**：v1 以 **MLX Swift + Gemma 4 E4B**（或視記憶體狀況降級 E2B）作為翻譯引擎，直接嵌入 App 進程，不依賴外部服務。開發初期可先用 Ollama 快速驗證 prompt 與翻譯品質，正式整合再切到 MLX。

## 硬體資源估算（M4, 16GB 基準）

| 元件 | 概估記憶體 | 備註 |
|---|---|---|
| WhisperKit（small，Core ML，量化） | ~250–500MB | 常駐，串流期間持續佔用 |
| Gemma 4 E4B（4-bit 量化） | ~2.5–3GB | 僅在觸發翻譯／摘要時載入運算，可考慮閒置時卸載 |
| Gemma 4 E2B（4-bit 量化） | ~1.3–1.8GB | 記憶體吃緊時的降級選項 |
| macOS + App 其餘 | 依系統狀況 | 16GB 機型需保守評估，避免與瀏覽器/會議軟體（Zoom/Chrome 本身就吃資源）搶記憶體 |

**設計含意**：翻譯不是連續運算，而是比照原專案「句尾觸發」的模式（`checkAndRotateSubtitle`）— 每個句子結束才丟給 Gemma 4 做一次翻譯，而非逐字即時翻譯。這讓 GPU/ANE 負載是陣發性的，而非持續佔用，較適合與 STT 串流並存於 16GB 機型。24GB+ 機型可考慮兩顆模型同時常駐以降低延遲。

## 風險與待驗證項目

1. **簡體 vs 繁體**：Whisper 對中文語音的輸出傾向簡體字；Gemma 4 翻譯目標語言雖可指定「繁體中文」，但仍需實測是否穩定產出繁體。建議加一層 **OpenCC（簡轉繁）後處理**作為保險機制，不論是 STT 直接輸出中文、或 Gemma 4 翻譯結果，統一過一次 s2twp（簡體→繁體台灣慣用語）轉換。
2. **端到端延遲**：「快速」是核心需求。需實測 音訊 chunk → WhisperKit partial result → 句子分段 → Gemma 4 翻譯 → 字幕更新 的總延遲，目標與原專案的雲端方案（數秒級）相當或更快。這是 Phase 0 的重點驗證項目。
3. **雙模型併發的記憶體壓力**：STT 常駐 + 翻譯陣發性載入，在 16GB 機型上與會議軟體本身（Zoom/Meet 網頁版）同時運行是否會觸發記憶體壓力／降頻，需要實機測試。
4. **語言自動偵測**：原文語言不一定固定（可能中英夾雜），WhisperKit 的語言偵測準確度與切換靈敏度需要驗證，避免頻繁誤判導致翻譯路徑錯亂（例如中文原文被誤判成英文又翻回中文）。
5. **首次啟動的模型下載體驗**：WhisperKit 與 Gemma 4 權重都需要首次下載（合計可能上看 3-4GB），需要設計對應原專案「輸入 API Key」步驟的「首次啟動下載模型」UX，且需說明所需硬碟空間與網路需求（僅此步驟需要網路）。

---

## 結論

| 項目 | 選型 |
|---|---|
| STT | WhisperKit（small，多語言，串流） |
| 翻譯 | Gemma 4 E4B（4-bit，MLX Swift，App 內嵌） |
| 簡繁轉換保險 | OpenCC s2twp 後處理 |
| 配音（TTS） | v1 排除，列為 Phase 6 stretch goal |
| 會議摘要 | 沿用同一顆 Gemma 4，長 context 直接摘要逐字稿 |

技術上可行，但「快速」與「16GB 機型可用性」兩項需要 Phase 0 用實機數據驗證後才能確認最終模型大小（E2B vs E4B、Whisper tiny/base/small）的預設值。
