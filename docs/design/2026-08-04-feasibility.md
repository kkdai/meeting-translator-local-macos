# 可行性評估：本地 STT + Gemma 4 翻譯

日期：2026-08-04（2026-08-05 依 Phase 0 spike 實測結果更新）
狀態：Phase 0 已驗證，結論由草案假設改為實機數據

---

## 目標與限制

- **硬體基準**：MacBook（Apple M4，假設 16GB 統一記憶體為最低支援規格；24GB+ 視為進階體驗）。
- **STT 要求**：「快速」、即時顯示**繁體中文**字幕。原文語言不限（英文、日文…），也可能本來就是中文。
- **翻譯要求**：使用比較小的本地模型處理翻譯 — 對應 Google 於 2026-04-02 發布的 **Gemma 4** 系列中最小的變體（E2B / E4B），而非舊版 Gemma 3。
- **完全離線**：不可依賴任何雲端 API（這是與原專案最核心的差異）。
- **延續原專案 UX**：懸浮字幕、雙語逐字稿匯出、會議筆記、網頁匯出。

---

## STT 選項評估

| 方案 | 優點 | 缺點 | 結論 |
|---|---|---|---|
| **WhisperKit**（Argmax，2026-05 起併入 `argmax-oss-swift` v1.0，MIT） | Core ML + ANE + Metal 原生加速；官方數據 base model（142MB）在 Apple Silicon 上達 >15x real-time（5 秒音訊約 0.3 秒處理完）；原生支援串流即時轉錄；多語言（沿用 Whisper 的 ~99 語言，含中/英/日/韓等會議常見語言）；MIT 授權；macOS 13+ 即可用，不綁定最新系統 | 需要下載模型權重（首次啟動）；中文輸出偏簡體，需後處理轉繁體 | **首選**：多語言穩定度與相容性最符合「會議來源語言不固定」的需求 |
| **Apple `SpeechAnalyzer` / `SpeechTranscriber`**（macOS 26 Tahoe+ 原生框架） | 完全免模型下載；ANE 加速下英文場景實測比 Whisper Small 快 ~3 倍、WER 更低；系統內建、零額外體積 | 僅 macOS 26+ 可用（排除較舊系統使用者）；官方測試多集中在英文，多語言／中文的 on-device 覆蓋與品質尚待驗證；客製化空間（如強制輸出格式、串流細節）不如 WhisperKit 成熟 | **候選 / 快速跟進項**：可作為 macOS 26+ 使用者的可選加速後端，但不作為 v1 唯一依賴 |
| whisper.cpp（純 C++，手動 Core ML 編碼器） | 社群成熟、可控性高 | 需要自行處理 Swift 橋接、串流管線、記憶體管理，工程成本高於直接用 WhisperKit（本質上是同一套 Core ML Whisper，WhisperKit 已經做好這層） | 不採用，WhisperKit 已覆蓋其優點且封裝更完整 |

**建議**：v1 以 **WhisperKit** 為唯一 STT 後端（模型選 `small` 或蒸餾版本，在速度與多語言準確度間取平衡；可在 UI 提供 tiny/base/small 選擇）。`SpeechAnalyzer` 列為 Phase 2+ 的可選加速路徑，待驗證中文與多語言 on-device 品質後再決定是否納入。

## 翻譯（MT）選項評估

Gemma 4（2026-04-02 發布）規格：E2B（~2.3B 有效參數）、E4B（~4.5B 有效參數）、26B A4B（MoE）、31B（dense）。E2B/E4B 支援文字＋圖片＋**音訊**輸入、純文字輸出，128K context，Apache 2.0，140+ 語言。

| 執行方式 | 優點 | 缺點 | 結論 |
|---|---|---|---|
| **MLX（MLX Swift）** | Apple 官方框架，直接呼叫 Metal，效能最佳（社群評測顯示比 Ollama 快 10-20%）；已有社群的 Gemma 4 MLX Swift 原生實作可參考；可直接整合進 App 進程內，無需額外背景服務 | 需要自行管理模型下載、量化版本、記憶體釋放；MLX Swift 生態相對新，API 穩定度需留意 | **首選**：效能與整合度最佳，且是與 WhisperKit 一致的「App 內直接跑」架構 |
| **Ollama（本地 REST API，`localhost:11434`）** | 整合極簡單（HTTP call）；模型管理、量化、更新都由 Ollama 處理；開發速度快 | 使用者需另外安裝 Ollama App 並手動 pull 模型，增加安裝步驟；效能略遜於 MLX 原生；多一個外部進程依賴，不符合「單一 App 直接可用」的產品體驗 | **備案**：可作為開發階段的快速原型驗證管道，正式產品不建議依賴外部進程 |
| llama.cpp + GGUF | 成熟、可控 | 需自行維護 Swift 綁定，量化格式與 MLX 生態分離，無額外優勢 | 不採用 |

**建議**：v1 以 **MLX Swift + Gemma 4 E2B**（Phase 0 實測後由原規劃的 E4B 改為 E2B，見下方硬體資源估算與結論）作為翻譯引擎，直接嵌入 App 進程，不依賴外部服務。E4B 列為使用者可選的更高品質選項。

## 硬體資源估算（M4, 16GB 基準）— 已用 Phase 0 spike 實測數字取代原本的磁碟大小推算

| 元件 | 磁碟大小（實測） | 常駐記憶體 RSS（實測） | 備註 |
|---|---|---|---|
| WhisperKit（small，Core ML，量化） | ~465MB | **126MB** | 常駐，串流期間持續佔用 |
| Gemma 4 E2B（4-bit 量化） | 3.3GB | **1928MB** | 全程常駐可行，見下方 |
| Gemma 4 E4B（4-bit 量化） | 4.8GB | 未單獨量測（預期高於 E2B，同量級） | 更高品質但延遲約 2 倍，v1 非預設 |
| WhisperKit + Gemma 4 E2B 同時常駐 | — | **1946MB（~1.9GB）** | 實測併發峰值，見 [2026-08-05 spike 結果](2026-08-05-phase0-spike-results-translation.md) |

**修正**：原本用磁碟大小類推記憶體用量，高估了 Gemma 4 的實際常駐記憶體（估 2.5-3GB，實測只要 1.9GB）。**16GB 機型的可用性遠比原本評估樂觀** — WhisperKit + Gemma 4 E2B 同時常駐只佔用不到 2GB，不需要「翻譯完就卸載模型」這類複雜的記憶體管理，兩顆模型可以在整場會議期間全程常駐，用「句尾觸發」（`checkAndRotateSubtitle`）決定何時做推論運算即可，不必額外用「是否卸載模型」做記憶體管理。24GB+ 機型的優勢主要展現在可以選用 E4B 甚至更大的 Whisper 模型（`base`/`large-v3-turbo`）而非記憶體餘裕本身。

## 風險與待驗證項目

1. ~~**簡體 vs 繁體**：Whisper 對中文語音的輸出傾向簡體字~~ — **Phase 0 實測推翻**：WhisperKit（tiny/base/small）在強制指定 `language: "zh"` 時直接輸出繁體中文，Gemma 4 的翻譯目標也穩定輸出繁體。OpenCC s2twp 後處理保留作保守防呆，但不再是已知必踩的坑。詳見 [2026-08-04 STT spike 結果](2026-08-04-phase0-spike-results.md)。
2. ~~**端到端延遲**~~ — **Phase 0 已驗證，遠超預期**：WhisperKit 三個模型皆達 20-74x 即時速度；Gemma 4 E2B 暖機後單句翻譯 0.35-0.43s、E4B 0.67-0.82s，兩者合計的端到端延遲遠低於原專案雲端方案的「數秒級」。唯一需要在正式產品處理的延遲議題是**首句冷啟動**（Metal kernel JIT 一次性成本，E2B 約 1.8 秒），需要用「按下開始後先送一句暖機」的機制吸收掉。
3. ~~**雙模型併發的記憶體壓力**~~ — **Phase 0 已驗證，無虞**：WhisperKit small + Gemma 4 E2B 同時常駐實測僅 ~1.9GB，16GB 機型有充裕空間，不需要複雜的記憶體管理（卸載/重載模型）機制。
4. **語言自動偵測**（仍待處理，Phase 0 發現且未解決）：Phase 0 測試發現 WhisperKit 的語言自動偵測在合成語音上會誤判（中文誤判成英文）。原文語言不一定固定（可能中英夾雜），需要在 UI 讓使用者可以明確指定或覆蓋來源語言，不能完全依賴自動偵測。這是 Phase 1（純 STT 移植）需要處理的項目。
5. **首次啟動的模型下載體驗**：WhisperKit（單一模型，例如 small ~465MB）與 Gemma 4 E2B（3.3GB）合計約 **3.8GB**，與原估計相近。需要設計對應原專案「輸入 API Key」步驟的「首次啟動下載模型」UX，且需說明所需硬碟空間與網路需求（僅此步驟需要網路）。
6. **中英夾雜場景**（新發現，待補測）：Phase 0 的合成測試音訊只驗證了純英文、純中文句子，真實會議常見的中英夾雜（例如中文會議夾雜英文術語）尚未驗證 WhisperKit 辨識與 Gemma 4 翻譯的品質，需要用真人錄音樣本在 Phase 1 補測。

## 結論

| 項目 | 選型 |
|---|---|
| STT | WhisperKit（`small`，多語言，串流） |
| 翻譯 | **Gemma 4 E2B**（4-bit，MLX Swift，App 內嵌）— 依 Phase 0 實測從原本規劃的 E4B 改為 E2B，速度快一倍且品質已足夠，E4B 列為進階選項 |
| 簡繁轉換保險 | OpenCC s2twp 後處理（防呆保險，非已知必要） |
| 配音（TTS） | v1 排除，列為 Phase 6 stretch goal |
| 會議摘要 | 沿用同一顆 Gemma 4，長 context 直接摘要逐字稿 |

**技術可行性已由 Phase 0 spike 實機數據確認**：STT 延遲、翻譯延遲、雙模型併發記憶體皆遠優於預期門檻。剩餘的開放問題是語言自動偵測穩定性、中英夾雜場景品質，兩者都排入 Phase 1 用真人錄音驗證。詳細數據見 [STT spike 結果](2026-08-04-phase0-spike-results.md) 與 [翻譯 spike 結果](2026-08-05-phase0-spike-results-translation.md)。
